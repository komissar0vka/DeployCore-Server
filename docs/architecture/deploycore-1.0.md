## Архитектура и границы доверия

- **Server** остаётся локальным источником данных и полномочий. Существующие API пользователей и агентов, Compose, Nginx, PostgreSQL, хранилище пакетов и TLS сохраняются. Ядро вычисляет права локально. Исходящий доступ к Cloud и репозиторию релизов настраивается отдельно. При отключении Интернета установка и инвентаризация продолжаются в рамках локальной политики.
- **Windows Agent** продолжает работать с локальным Server по HTTPS. Расширения протокола объявляются через capability, выдача новых payload ограничивается поддерживаемыми версиями. Сохраняются доверенный CA, UUID, ключ и DPAPI-состояние. Агент получает только типизированные операции для утверждённых пакетов, проверки обнаружения и, позже, обновления самого агента.
- **Cloud** использует собственную БД. Домены модели: организации, пользователи и роли, экземпляры и открытые ключи, тарифы и цены, подписки, выдачи, активации и отзывы, каталог релизов и аудит. API приёма активаций отделяется от админ-панели. Идентификатор экземпляра, доказательство владения ключом и версия протокола достаточны для активации. Cloud не получает адреса агентов, инвентарь, пакеты и задания. Нет входящего соединения в клиентскую сеть и канала управления устройствами.
- **Update Center** показывает версии, changelog, совместимость и историю в Server. Операции на хосте выполняет отдельный локальный updater. Первая версия запускается оператором на хосте по идентификатору подписанного релиза. Для последующей автоматизации — расписание хоста или локальный запрос с фиксированной схемой, RBAC, подтверждением и локальной политикой. Основной веб-контейнер не подключается к Docker socket. Updater с доступом к Docker привилегирован на хосте. Его входы ограничиваются заранее заданными проектом, конфигурацией, путями, разрешёнными образами и операциями. Произвольные shell-аргументы, Compose из релиза и команды Cloud исключены.

Предлагаемая структура дополняет текущую. Имена предварительные.

```text
apps/server/deploycore/licensing/    локальная проверка, права, аудит, квота
apps/server/deploycore/updates/      статус, совместимость и история для UI
apps/web/src/                       продолжение существующей консоли
apps/agent/                         совместимый агент и обновление службы
apps/cloud/                         API, админ-панель, отдельная цепочка миграций
apps/updater/                       хостовый CLI и локальный журнал восстановления
packages/api-contract/              контракт действующего Server
packages/licensing-contract/        схемы, форматы и тест-векторы
packages/update-contract/           схемы релизов и совместимости
deploy/cloud/                       отдельный Compose и окружение Cloud
deploy/updater/                     шаблоны локального запуска и прав
deploy/scripts/                     install, upgrade, backup, restore, diagnose
```

Для Server сохранить `/api/v1` и действующие контракты агентов. Новый API лицензии, обновлений и предпросмотра добавляется отдельными маршрутами. Чтение статуса доступно согласно роли, импорт и смена политики защищены Super Admin, CSRF и аудитом. У Cloud независимо версионируются клиентский API активации и административный API. Публикация не меняет тарифы и подписки, а операции с тарифами не предоставляют доступ к инфраструктуре релизов.

## Лицензирование

| Тариф | Предлагаемая политика |
| --- | --- |
| Free | 5 управляемых устройств, без учётной записи Cloud. Инвентаризация, каталог и развёртывания доступны |
| Business | Квота 20, 50, 100 или произвольная. Срок 1 или 12 месяцев. 49 ₽ за устройство в месяц — исходное предложение, цена и валюта хранятся в Cloud |
| Enterprise | Индивидуальная квота, выдача файла активации для автономной сети, условия поддержки определяются договором |

- Экземпляр хранит постоянный UUID и отдельную пару ключей активации. Приватный ключ **экземпляра** находится локально вне образов, резервируется вместе с конфигурацией. Приватный ключ **выдачи лицензий** хранится в контуре Cloud, предпочтительно KMS/HSM. Файл запроса содержит UUID, публичный ключ и одноразовый идентификатор. Cloud фиксирует его потребление и привязку в транзакции. При переносе предусмотрены перенос идентичности с выводом старого узла из эксплуатации или перевыпуск с отзывом старой активации.
- Файл лицензии содержит версию конверта, `kid`, точные байты полезной нагрузки и подпись Ed25519. Подписываются идентификаторы лицензии, активации и экземпляра, отпечаток публичного ключа, редакция, лимит, `issued_at`, `not_before`, `expires_at`, `grace_until`, номер выдачи и разрешённые возможности. Подпись покрывает также контекст формата и идентификатор ключа. Проверка ограничивает размер, разбирает строгую схему, сверяет привязку и время UTC. Клиент хранит принятую выдачу и водяной знак её номера, чтобы старый документ не замещал новый. [RFC 8032](https://www.rfc-editor.org/rfc/rfc8032)
- Ротация через доверенный подписанный набор ключей с версией, перекрытием ключей и импортом офлайн. Раздельные корни доверия лицензий и обновлений. Отзывы передаются подписанным монотонным списком, который можно обновить онлайн или импортировать файлом. Подтверждённый отзыв прекращает коммерческие права без удаления данных. В полностью закрытой сети отзыв начинает действовать после доставки списка. Клон всего состояния вместе с ключом невозможно надёжно отличить от оригинала офлайн. Онлайн Cloud ограничивает выдачи и обнаруживает конфликтующие активации, а локальный журнал помогает обнаруживать регресс номера и сбой часов. Владелец хоста способен изменить клиентский код.
- Слот считается по уникальному UUID устройства со статусом «управляется». Offline и отзыв ключа слот сохраняют. Повтор того же запроса идемпотентен, адресное восстановление прежнего UUID использует тот же слот. Новый ПК получает новый UUID. Явное снятие с управления прекращает выдачу новых заданий и освобождает слот, но сохраняет карточку, историю и инвентарь. Для активной попытки сначала дождаться завершения или разрешить неопределённый исход. Обратное включение потребляет слот. Старый DELETE сохраняет существующий контракт, продуктовый UI предлагает снятие с управления первым.
- Ввести общий порядок блокировок для транзакций изменения квоты и управляемого состояния. Под общей блокировкой экземпляра прочитать действующие права и число слотов, затем записать переход устройства, использование токена и аудит. Простое создание токена не резервирует слот. При отказе токен не расходуется. Для замены ПК предусмотреть атомарное переназначение освобождённого слота через подтверждённый процесс без объединения аппаратных идентичностей. Конкуренцию проверять на PostgreSQL запросами с разными UUID и токенами.
- Действующая лицензия работает автономно. После истечения предлагаем 14 дней grace с сохраняемой квотой и уведомлениями. Затем Free с лимитом 5. Уже управляемые устройства сверх лимита продолжают работать, новые регистрации и возврат снятых с управления запрещаются, пока число слотов не станет меньше лимита. Такая же политика предлагается для первой миграции и снижения квоты. Доступ к UI, аудиту, восстановлению и импорту сохраняется. Записывать активацию, смену состояний, отзыв, перенос и отказ по квоте без сырых документов, ключей и токенов.

## Механизм обновлений

1. Cloud публикует релизы Stable и Beta, changelog и подписанные метаданные. Предлагается клиент для TUF с доверенным корнем, ролями, сроками и версиями метаданных, ограничением длины и SHA-256 для артефактов. CI публикует OCI-образы по digest, отдельные Windows-артефакты с Authenticode и офлайн-комплект. Релиз описывает архитектуру, допустимые исходные версии, исходные и целевые ревизии БД, диапазоны протоколов агента, минимальные версии updater и платформы и возможность отката. Просроченные или регрессивные метаданные блокируют обновление. Текущая установка продолжает работу. [Спецификация TUF](https://theupdateframework.github.io/specification/latest/)
2. Updater сериализует запуски, проверяет подпись, размер и хеш, совместимость, место для старых и новых образов и копий, текущие контейнеры, тома и конфигурацию. Администратор выбирает релиз и окно обслуживания. До миграции сервер прекращает приём новых заданий и выдачу стартов, активные попытки завершаются либо сверяются оператором. Перед точкой резервного копирования останавливаются прикладные записи. Согласованная копия включает БД, пакеты, конфигурацию, TLS и идентичность экземпляра. Копия закрыта правами и проверяется контрольными суммами, пробным восстановлением PostgreSQL отдельно, проверкой ревизии и соответствия файлов каталогу.
3. Updater сохраняет предыдущие digest и состояние операции, применяет проверенные образы и миграцию с общей блокировкой запуска. Сверяет Alembic, HTTPS, liveness/readiness, API и чтение каталога; публикует результат. При сбое до изменения схемы возвращаются предыдущие образы. После миграции простой откат образов допустим только при явно проверенной совместимости. Иначе восстановление совместимой пары «БД + файлы + конфигурация» репетируется из копии. Автовосстановление допустимо до открытия записей при подтверждённой целостности точки восстановления; после возобновления записей требуется решение оператора о переносе или потере новых данных. Неопределённые попытки не переотправляются автоматически после восстановления.
4. Агент получает обновление только от своего Server после назначения на согласованную пилотную группу. Проверяет собственную совместимость, размер, хеш, подпись релиза и Authenticode. Отдельный локальный помощник с ограниченным интерфейсом обновляет службу в простое, сохраняет идентичность и предыдущую рабочую версию, проверяет запуск и heartbeat. Волны имеют лимит параллельности и пороги остановки по сбоям. Остановка блокирует новые назначения, уже начатые доходят до безопасной точки. Статусы и причины публикуются по каждому устройству. Рабочий агент остаётся совместимым до явного выбора устройства для обновления.

## Интерфейс и обнаружение

- Сохранить оболочку, общие компоненты, URL, роли, RU по умолчанию, EN и выбор темы. Обзор показывает здоровье, устройства, текущие и проблемные задания, последние события. «Устройства» объединяют связь, ОС, характеристики и историю. «Пакеты» показывают версии, источник утверждения и результаты правил. «Развёртывания» показывают цели, этапы, неопределённый исход и безопасный повтор. «Агенты» показывают версии, состояние и волны. У «Лицензии», «Обновлений», «Аудита» и «Настроек» свои права и ошибки. Общие требования — фильтры и пагинация с сохранением состояния, клавиатурная навигация, читаемые статусы, адаптивные таблицы и подтверждение операций с показом последствий.
- Setup остаётся одноразовым. Сначала диагностика HTTPS и компонентов, затем организация и локальный URL, первый администратор и показ Free. Режим TLS и пути сертификатов задаёт установщик на хосте. Браузер проверяет фактически доступный HTTPS, показывает инструкции, а токен агентов создаётся после входа. Первичная настройка не открывается для обновлённых экземпляров.
- Модель обнаружения использует версионированные типизированные листья и ограниченные `all`/`any`. Для каждого листа различать «найдено», «отсутствует», «проверка недоступна». В `all` доказанное отсутствие определяет результат, в `any` — доказанное наличие, иначе неизвестность сохраняется до получения достаточных данных. Существующие одиночные правила сохраняют текущую семантику. Сверить MSI в нужных контекстах и отдельно согласовать поддержку per-user. Файловые правила работают на локальных путях и сохраняют действующие ограничения на reparse points.
- Предпросмотр — отдельная ограниченная операция под RBAC, CSRF и аудитом, на выбранном тестовом устройстве, с capability, тайм-аутом и лимитом запросов. Это проверка метаданных обнаружения без скачивания или запуска установщика, без shell и без передачи содержимого файлов. Результат установки отдельно хранит факт запуска, код процесса, результат обнаружения, необходимость перезагрузки и подтверждённый итог. При требуемой перезагрузке выполнять ограниченную повторную проверку, без повторного запуска MSI/EXE. Диагностика по умолчанию структурированная, сырые логи — только после согласования срока хранения, редактирования чувствительных данных и доступа.

| 0 | Схема остаётся на `0006_manual_approval`. Миграции и код этапа 0 не добавляются |
| 1 | Следующая ревизия — добавочные поля/таблицы для правил, наблюдений и диагностического результата. Существующие правила читаются как одиночные. Новые агенты поддерживают оба представления; старым выдаются только совместимые задания. Историческим попыткам не приписывается результат проверки |

| 3 | Стабильная идентичность, журнал выдач/отзывов, статус управления и индексы квоты. Добавить поля, заполнить из текущих устройств, сверить итог, затем включить ограничения. Не менять UUID, старые ключи, инвентарь и ссылки заданий. Секрет экземпляра создаётся и резервируется установщиком отдельно от Alembic |
| 4 | Отдельная миграционная линия Cloud. Транзакционные ограничения на привязку и идемпотентность выдачи. Без общих таблиц, учётных записей или сети БД с Server |
| 5 | Добавочные таблицы отчётов, волн и исходов. Журнал хостового updater хранится вне PostgreSQL, чтобы пережить её откат. Схема новых модулей включается только после проверки совместимости |
| 6 | Публикуется матрица поддерживаемых исходных версий и процедуры восстановления. Удаление наследуемых полей откладывается до отдельного подтверждённого релиза |

Перед каждой будущей миграцией — новая проверенная копия. Матрица включает чистую установку, переход с `0006`, предыдущий поддерживаемый релиз, проверку модели Alembic и восстановление после прерывания. Тестовые фикстуры должны включать старого агента, пакеты с обоими типами утверждения и очередь с активной и неизвестной попыткой. Номера после `0006` резервируются при реализации. По умолчанию используются добавочные изменения, затем переключение читателей и писателей и только после окна совместимости возможна очистка.

## Риски и зависимости

| Риск | Меры и зависимость |
| --- | --- |
| Повторный запуск после сбоя или восстановления | Сохранять старт и идентификаторы очереди, тестировать обрыв на границах, оставлять спорные попытки на сверку. Нужны управляемые Windows-стенды и безопасные MSI/EXE-фикстуры |
| Неверное определение ПО | Отделить scope, доступ и отсутствие, подтвердить различия реестра, MSI и перезагрузки на LocalSystem. Не расширять автоматический повтор по одному коду выхода |
| Кража ключа подписи или поставка повреждённого релиза | Независимые ключи, разделение ролей, журнал выдачи, проверка артефактов и аварийная ротация. Нужны хранилище ключей, Windows-подпись и CI |
| Двойная активация или неверное время | Привязка к ключу, история выдач и перенос, диагностирование сдвига часов. Полный клон и отзыв без доставки учитываются в условиях продукта |
| Откат БД при изменённых данных | Окно обслуживания, барьер записей, совместимая копия, проверенный restore и согласованная точка восстановления. Нужны запас диска и целевые RPO/RTO |
| Updater имеет доступ к хосту | Узкий интерфейс, локальная авторизация, allowlist операций и никакого Docker socket у приложения. Отдельный security review обязателен до автоматизации |
| Утечки в диагностике и Cloud | Минимальный набор полей, ограничение ролей, проверка egress, маскирование и политика хранения. Отдельное согласование обработки данных и оплаты |
| Невоспроизводимый выпуск | Зафиксировать код ручного утверждения вместе с миграцией, пинить релизные образы по digest и сохранить матрицу совместимости. Публиковать только после проверок |

## Решения на согласование

1. Подтвердить 14 дней grace, учёт offline/отозванных устройств, сохранение работы при превышении лимита и процедуру замены ПК.
2. Решить, какие тарифы получают офлайн-файл, какой срок допустим для полностью автономной активации и как клиент в закрытой сети получает подписанные отзывы.
3. Утвердить тарифные возможности, ценовые параметры, условия поддержки и будущий платёжный контур.
4. Выбрать владельца KMS/HSM, модель хранения корневых ключей, процедуру ротации и выпуск сертификата Authenticode.
5. Утвердить для первой версии запуск обновлений оператором, правила Stable/Beta, пилот и пороги остановки, границы автоматического восстановления, RPO/RTO и окна обслуживания.
6. Согласовать матрицу Windows, поддержку per-user MSI и реестра, тестовые ПК и фикстуры для этапа 1, политику хранения логов.
7. Согласовать макеты этапа 2, поддержку TLS через собственный CA или внешний reverse proxy, права и доступ к административным разделам.
8. Подтвердить оператора Cloud, регион и срок хранения метаданных, точный набор полей, допустимый исходящий трафик и требования к нагрузке.
