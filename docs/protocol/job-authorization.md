# Авторизация выполнения задания

Контракт строгого профиля в разработке beta.5. Агент beta.4 использует аутентифицированный TLS, аренду и журнал попытки.

## Граница доверия

Для строгого профиля устройство получает доверенные ключи из локальной конфигурации или GPO. Выбор доверенного профиля и его минимальной версии хранится вне входящих запросов Server. Ключи заданий отделены от ключей лицензирования и обновления. Опциональная доверенная политика должна уметь разрешать операции и неизменяемые SHA-256 независимо от назначения Server.

## Подписываемые данные

Использовать Ed25519 и явное разделение контекста. Подпись покрывает версию формата, идентификатор ключа и точные UTF-8 байты полезной нагрузки. Нагрузка содержит идентификаторы задания, цели, попытки, версии и устройства, операцию, времена выдачи и окончания, а также полный манифест исполнения. Манифест содержит SHA-256 и размер файла, параметры запуска, обнаружение, тайм-аут и допустимые коды выхода. Смена любого поля требует подписи заново.

Обязательные отрицательные проверки охватывают неизвестный ключ, изменённый манифест, другой UUID, неверную аренду, повторяющиеся JSON-поля, истёкший срок и отказ локальной политики. Проверка выполняется до получения исполняемого файла и повторно перед стартом. Повторная аренда Server не продлевает подписанный срок.

## Старт и совместимость

Перед стартом агент записывает идентификатор попытки в устойчивое состояние. Серверный барьер старта и идемпотентность результата остаются действующими. Если процесс мог запуститься, агент выясняет состояние через проверку обнаружения и сообщает неопределённый результат, когда проверка невозможна. Удаление истории повторов допустимо после окончания абсолютного срока соответствующей подписи.

Старый агент сохраняет прежний контракт только в явно разрешённом профиле совместимости. Агент строгого профиля принимает только подписанный контракт. Перекрытие старого и нового доверенных ключей выполняется через управляемое изменение профиля с определённым сроком отзыва.

## Как проверить реализацию на стенде

Server публикует дополнительный endpoint авторизации. Старый endpoint манифеста продолжает обслуживать beta.4. Для строгого агента сначала установите локальную политику `job-trust.json` в защищённый каталог состояния `%ProgramFiles%\DeployCore` под управлением администратора Windows. Установите её через GPO или локальное администрирование и перезапустите службу. Изменение политики через API Server отсутствует.

Политика содержит `keys`, словарь идентификаторов ключей и публичных Ed25519 ключей в base64url без дополнения, а также `manifest_operations`, словарь SHA-256 подписанного JSON манифеста и списка разрешённых операций. Хеш покрытия вычисляется по точным UTF-8 байтам объекта `manifest`, сериализованного в компактный JSON с отсортированными ключами и ASCII-экранированием. Параметры запуска, обнаружение и прочие поля входят в хеш. Перед внесением записи проверьте весь манифест независимо от операторов Server. Для плановой ротации распределите оба публичных ключа, переключите выдачу на новый идентификатор, затем отзовите старый в локальной политике.

На тестовом Server укажите отдельный PEM Ed25519 только для подписи заданий. Compose override `deploy/compose.job-signing.yaml` читает `DEPLOYCORE_JOB_SIGNING_HOST_KEY` и `DEPLOYCORE_JOB_SIGNING_KEY_ID`. Закрытый ключ хранится вне репозитория, доступен для чтения пользователю контейнера и не должен совпадать с ключами лицензий или обновлений. Строгий агент не принимает неподписанный API. Если ключ доступен скомпрометированному Server, локальное разрешение по хешу манифеста и операции ограничивает набор действий. Компрометация Windows SYSTEM остаётся отдельным сценарием.

Агент проверяет подпись, срок и назначение до получения артефакта. Перед стартом он повторно проверяет срок и сохраняет идентификатор цели в DPAPI-журнале на 24 часа. Результат при повторе остаётся отказом даже при смене идентификатора попытки, пока идёт этот срок. После начала строгого режима наличие журнала блокирует работу при исчезновении файла политики. Операторский повтор создаёт отдельную цель. Ротация и снятие политики требуют локального администрирования.

Включение профиля предназначено для изолированной проверки. Сохранение дополнительного Compose override при самостоятельном переключении версии Server, доставка политики и управление ключами из панели требуют отдельной интеграции.
