## Как работает готовый MSI

1. При первичной настройке DeployCore администратор указывает HTTPS-адрес, доступный с Windows. Для уже настроенного экземпляра адрес задаётся в «Настройках». Сертификат TLS должен покрывать выбранный IP или DNS-имя.
2. В разделе «Установка агента» оператор выбирает срок и лимит регистраций и нажимает «Скачать готовый MSI». При необходимости он добавляет проверенный CA в PEM.
3. Адрес и временный токен включены в MSI. Пакет предназначен для новой установки и требует прав администратора. Windows Installer создаёт службу, агент сохраняет настройки в DPAPI и регистрируется при доступе к серверу, пока токен действителен.
4. MSI передаётся только авторизованным получателям. Токен можно отозвать в панели. Обычный MSI с ручной настройкой доступен отдельно.

## Проверено и что остаётся

- Последний прогон прошёл 63 теста pytest, Go test и vet, кросс-сборку Windows amd64, TypeScript/Vite, Chromium и изолированный Compose smoke. Подтверждены ввод адреса, RBAC/CSRF, структура MSI, параметры службы и расход одноразового токена тестовым клиентом.
- На предыдущем блоке отдельно проверены миграция `0007 → 0008` с сохранением инвентаря и пять успешных регистраций из шести одновременных запросов Free.
- **DeployCore 1.0 ещё не принят к выпуску.** На доменной и недоменной Windows предстоит проверить запуск готового MSI, появление ПК в панели, перезапуск службы с сохранением UUID, удаление MSI и отказ при существующем агенте. Для этапа 1 остаются реальные MSI/EXE, ошибки реестра, перезагрузка, обрывы связи и совместимость Agent 0.3.4.
- Для этапа 3 остаются подписанные отзывы, процедура ротации доверенных ключей и проверка восстановления из резервной копии. Cloud представлен [черновым контрактом](../../packages/licensing-contract/cloud-openapi.json). Cloud и Update Center в production не развёрнуты.

## Границы работы

По последнему отчёту рабочий DeployCore использует порт `8444` и остаётся на прежней версии. Изменения рабочего экземпляра, БД, TLS, секретов и рабочих агентов требуют отдельного согласования. Реальные задания установки и публикация Cloud или обновлений также требуют отдельного согласования. Проверки выполняются с временными данными и на выделенных стендах. FlipHunter, n8n и Xray не затрагиваются. Рабочие тома и данные сохраняются. Глобальная очистка Docker и `git push` запрещены без отдельного согласования.
