# DeployCore 1.0 · этап 1

## Обнаружение и исполнение

- `installed` подтверждает наличие ПО, `not_installed` подтверждает его отсутствие в области правила, `unknown` означает неполную проверку.
- Registry Uninstall проверяет обе WOW64-проекции HKLM. Имя сравнивается без учёта регистра, версия должна совпасть. Ошибка перечисления, открытия подраздела или чтения значения оставляет `unknown`, если совпадение не найдено. Отсутствие ключа или значения обрабатывается отдельно. MSI ProductCode проверяется из LocalSystem. Per-user MSI и пользовательские ветки реестра требуют отдельного согласования.
- Файловые правила ограничены локальным фиксированным диском и отклоняют reparse points. Для правила версии читается ресурс версии.
- `all` возвращает `not_installed`, если одно правило доказывает отсутствие. `any` возвращает `installed`, если одно правило доказывает наличие. При отсутствии определяющего результата неполная группа даёт `unknown`. Версия формы группы — 1, размер — от 2 до 8 листьев. Для удаления MSI требуется ровно одно правило с ProductCode, в том числе внутри группы.
- Недоступность обнаружения до запуска завершает попытку с `detection_failed`. После запуска она даёт неопределённый исход. Подтверждённое несовпадение после допустимого кода завершения даёт `detection_mismatch`.
- При принятом результате с кодом 3010, 1641 или флагом перезагрузки цель переходит в `awaiting_reboot` на срок до 24 часов. Агент сохраняет код процесса сразу после выхода. После смены загрузки он проверяет сохранённое правило и при обрыве связи повторяет доставку результата. Проверка относится к той же попытке. Агент не инициирует перезагрузку. Аварийное выключение до сохранения кода процесса оставляет исход для ручной сверки.
- Карточка задания показывает разрешение запуска, наблюдавшийся запуск процесса, стадию, код завершения, объём вывода, причины и результат после перезагрузки. Сервер получает размер вывода.
- Миграция `0007_detection` добавляет поля попытки и таблицу предпросмотров. Исторические наблюдения остаются пустыми. Agent 0.3.4 сохраняет формат одиночных правил и старый формат результата.

## Предпросмотр

В каталоге откройте версию и нажмите «Проверить обнаружение». Выберите тестовое устройство с Agent 0.3.5+. Проверка доступна и для черновой версии. Administrator и Super Admin могут создавать запросы с проверкой Origin и CSRF. За две минуты допускается один запрос на устройство и до пяти на оператора. Аудит фиксирует запрос и наблюдение. Агент получает ID запроса и правило и возвращает одно из трёх состояний. Он проверяет метаданные без скачивания или запуска установщика, командной оболочки и передачи содержимого файлов.

## Автоматические проверки

- 38 тестов pytest, совпадение OpenAPI и единственный Alembic head `0007_detection`.
- `go test -race ./...`, `go vet` для Linux и Windows, кросс-сборка агента и тестового бинарника Windows amd64.
- TypeScript/Vite и Chromium с тестовым API. Проверены редактор группы, предпросмотр, состояние `unknown` и отображение ожидания перезагрузки.
- Изолированный Compose. Проверены переход через `0006_manual_approval`, `alembic check`, TLS, SHA-256 для EXE/MSI, прежний протокол агента, выдача по capability, предпросмотр с RBAC/CSRF и лимитами, повторная доставка результата и истечение срока проверки. Использовались синтетические устройства.

## План приёмки на реальной Windows

Подготовить доменную и недоменную Windows x64, изолированный сервер с тестовым CA и снимки машин. Использовать тестовые MSI/EXE с маркерами версии и счётчиком запусков. Оставить отдельное тестовое устройство с Agent 0.3.4.

| Проверка | Ожидаемый результат |
| --- | --- |
| Тихая установка и удаление MSI/EXE из LocalSystem | Верный итог, код, одна попытка и корректный признак запуска. Переустановка обнаруженной версии и удаление отсутствующей версии пропускают запуск |
| Обе проекции HKLM Uninstall | Совпадение в любой проекции даёт присутствие. Полный поиск без совпадений даёт отсутствие. Недоступный подраздел или неожиданный тип значения оставляет неопределённость при отсутствии подтверждённого совпадения |
| Файл, ресурс версии, отсутствующий путь, junction и MSI ProductCode | Верные состояния. Отдельно зафиксировать видимость per-user MSI из LocalSystem |
| Составные правила | Подтверждённый отрицательный лист определяет `all`, положительный определяет `any`. Остальные неполные группы дают неопределённость |
| Предпросмотр, права, срок и аудит | Viewer и запрос без CSRF отклоняются. Второй агент не получает чужую проверку. Офлайн-запрос истекает. Счётчики скачиваний и запусков неизменны |
| Коды 3010/1641 и флаг перезагрузки | Перезапуск службы оставляет проверку ожидающей. Перезагрузка Windows даёт одну проверку в той же попытке. Проверить успех, несовпадение, недоступность и неизменный счётчик запусков |
| Потеря сети до старта, после старта и при отправке проверки | Исход сохраняется как неопределённый, если его нельзя доказать. Отправка восстанавливается из журнала. По истечении срока доступна ручная сверка |
| Agent 0.3.4 | Heartbeat, инвентарь и одиночные задания работают по прежнему контракту. Новые задания и предпросмотр проверяются на отдельном Agent 0.3.5 |

Реальная доменная и недоменная Windows и внешний Windows CI в этом прогоне недоступны. Критерий выхода этапа 1 остаётся открытым.

### Протокол прогона

1. На каждом стенде записать образ и сборку Windows, контекст службы, версию агента и SHA-256 фикстур. Перед первым заданием сделать снимок машины. Для агента 0.3.4 использовать отдельную машину.
2. Для каждого прогона сохранить ID цели и попытки, исходный и итоговый результат обнаружения, код процесса и счётчик запусков фикстуры. Тесты реестра и DPAPI можно предварительно прогнать на стенде командой `go test -v ./...` из `apps/agent`.
3. Для сценария с перезагрузкой сначала перезапустить только службу, затем выполнить полноценную перезагрузку Windows. Для сценария потери связи отключать доступ тестовой машины к тестовому серверу и сверить журнал после восстановления соединения.
4. После прогона сохранить аудит и журнал событий тестовой системы, удалить выданные тестовые ключи и вернуть машины к снимкам.
