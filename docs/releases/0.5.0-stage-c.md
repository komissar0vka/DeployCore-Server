# DeployCore 0.5.0 · этап C

## Протокол и безопасность

Этап C использует очередь этапа B. Существующие задания мигрируют в `transport_only`. На сервере режим исполнения включается через `DEPLOYCORE_ENABLE_EXECUTION=1`. По умолчанию сохраняется режим проверки транспорта. Версия Agent 0.3.4 заявляет `X-DeployCore-Capabilities: execute_v1` при poll. Сервер дополнительно проверяет версию агента из последнего heartbeat. Старым агентам выдаются только транспортные задания. Для установки достаточно роли Administrator или Super Admin, удаление и ручное разрешение неопределённого исхода требуют Super Admin.

Маршруты агента используют существующий Bearer-ключ устройства:

- `GET /api/v1/agent/{device_id}/jobs/{target_id}/manifest?attempt_id={uuid}`
- `GET /api/v1/agent/{device_id}/jobs/{target_id}/artifact?attempt_id={uuid}`
- `POST /api/v1/agent/{device_id}/jobs/{target_id}/start` с `attempt_id`

Манифест и артефакт доступны владельцу текущей подтверждённой попытки с действующей арендой до старта. Файл выбирается по утверждённой версии на сервере. Клиентские имена файлов не используются как пути. Сервер поддерживает Range и повторное скачивание. Агент при повторе скачивает файл целиком, проверяет размер, свободное место и SHA-256 до запуска. Authenticode проверяется сервером при утверждении версии. TLS-проверка и запрет HTTP-редиректов сохраняются.

Агент сохраняет отметку о намерении запустить процесс в DPAPI до запроса `start`. Атомарный серверный барьер выдаёт разрешение на старт один раз. Тот же процесс поддерживает lease через heartbeat. При сбое между разрешением и подтверждённым результатом, таймауте или неопределённом состоянии агент фиксирует `unknown` и не запускает установщик повторно. Повторная передача уже сохранённого результата идемпотентна. `Unknown` блокирует следующую выдачу на этот компьютер до ручного решения.

- `POST /api/v1/deployments/{job_id}/targets/{target_id}/resolve` с `verified_stopped: true` фиксирует ручную сверку просроченной или неопределённой попытки. Перед подтверждением проверьте отсутствие процессов установки и фактическое состояние пакета на Windows.
- `POST /api/v1/deployments/{job_id}/targets/{target_id}/retry` с новым UUID `request_id` создаёт новое задание после ошибки. Неопределённая попытка сначала требует ручного решения.

## Исполнение

MSI запускается через системный `msiexec.exe`. Агент сам задаёт `/i` или `/x`, `/norestart` и тихий режим по умолчанию `/qn`. В каталоге можно указать `/qb` и MSI properties. Подмена источника, пакета, патча, трансформации и политики перезагрузки через аргументы запрещена. Для MSI-удаления требуется правило ProductCode. Для EXE удаления требуется отдельный массив аргументов в утверждённом манифесте. Запускается тот же утверждённый EXE, поэтому произвольный путь к деинсталлятору или команды из реестра не поддерживаются.

Оба типа запускаются через CreateProcess с явно заданным приложением, отдельным рабочим каталогом и Windows Job Object. Процесс сначала создаётся приостановленным, затем входит в Job Object и возобновляется. Таймаут и отмена завершают дерево в пределах Job Object. Windows Installer service может выполнить работу вне этого дерева; такой исход помечается как неопределённый. Признак перезагрузки и коды 3010/1641 не подменяют проверку результата.

Доступны MSI ProductCode, точные имя и версия из 32/64-битного реестра HKLM, наличие локального файла и его Windows FileVersion. Для обновления задайте условие, отличающее целевую версию. Если условие уже выполнено, агент сообщает `already_installed`, а для удаления при отсутствии целевой записи — `already_absent`. Успех установки требует выполнения правила после допустимого кода выхода; для удаления правило должно перестать выполняться.

Панель показывает журнал этапов, диагностический код, код выхода и объём вывода. Raw stdout/stderr читаются и отбрасываются, чтобы случайные секреты из стороннего установщика не попали в БД. Системный MSI verbose log `/L*v` можно включить локально переменной `DEPLOYCORE_LOCAL_MSI_LOG=1` для службы. Он хранится во временном административном каталоге попытки, не отправляется на сервер и удаляется при штатном завершении. После аварийного завершения остатки каталога следует обрабатывать как приватные данные. Журнал DPAPI и серверные события сохраняются.

## Обновление и первая операция

1. Проверьте этап в отдельном Compose-проекте. Сделайте согласованную резервную копию PostgreSQL и тома пакетов перед обновлением рабочего экземпляра. Миграция `0005_execution` добавляет режим, этапы и результаты. Автоматический downgrade закрыт, откат схемы выполняется восстановлением предшествующей резервной копии.
2. Для выделенного ПК скачайте Agent 0.3.4 и сверяйте `SHA256SUMS`. Для уже зарегистрированного ПК завершите текущий обмен заданиями и удалите старую службу штатной командой `uninstall`. Установите новый MSI/EXE и снова зарегистрируйте службу с прежним HTTPS-адресом. Агент переиспользует сохранённое DPAPI-состояние и ключ. При необходимости укажите тот же доверенный CA. Сверьте 0.3.4 и heartbeat в карточке устройства.
3. На выделенном тестовом экземпляре задайте `DEPLOYCORE_ENABLE_EXECUTION=1` в Compose и примените конфигурацию. В разделе «Программы» загрузите подписанный установщик, задайте подходящие аргументы и правило обнаружения, утвердите версию и нажмите «Установить».
4. Выберите тестовый ПК, проверьте версию, аргументы и список устройств и подтвердите запуск. В деталях задания проверьте фактическую стадию, итог обнаружения и код выхода. Для обновления создайте и утвердите новую версию с правилом обнаружения её версии. Для удаления переключите операцию под ролью Super Admin.
